# Weekly Progress — spec generation (2026-08-11)

## Progress

### 1. Spec generation for the Rust standard library

I reran all 2,121 Rust standard-library targets using Argus: **127 generated
specs were accepted and 1,994 were skipped** after semantic and source-fidelity
checks.

I changed the experiment granularity from running across the whole
std library (function-level) to module-level.
- For `core::slice`, all **132** stable APIs are covered: 12 existing specs and
  120 generated specs. The determinism check reports `45 incompleteness`.
- For `alloc::vec`, **48/49** stable APIs are covered: 24 existing specs and
  24 generated specs, and one justified as no-spec (`Vec::splice`). The determinism check reports `4 incompleteness`.


## Questions for discussion

1. **How should we review generated specifications?**  
   We have already generated specs for modules such as `slice`. Is it sufficient to generating proofs and using verus to verify them, or do we also need a separate review?
   - It is consuming to review all top-level functions, as all 132 functions can be called by users.

2. **Which modules are worthwhile targets for spec generation?**  
   Do we have criteria for selecting the next modules? My preliminary view is
   that the most challenging targets may be APIs involving external system state,
   such as `getcwd()`, or APIs involving `unsafe` code.

3. **Spec checking on issue solving, suggested by Fan**  
   I am also exploring specification checking in issue-solving settings, such as SWE-bench Pro. I found some cases where the issue description is incomplete or ambiguous and does not uniquely imply the ground-truth patch/test behavior. Should we also make some progress in this direction, e.g., by studying how to improve the quality of issue descriptions/patches?
